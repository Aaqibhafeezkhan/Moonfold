# Limit signals for provider handoff

A handoff offer (or an automatic handoff) starts when a run ends with a failure of class
`usage_limit`. Each adapter decides that class from what its provider reports. This page lists
what each one reads today, so a maintainer adding a provider knows what to map. Retries the
provider performs on its own (a transient 429 it will retry) never start a handoff; only the
failure that ends the run does.

| Provider                                      | Signal Moonfold reads                                                                                                                                                                          | Reset time                                                                                                                                                                | Source                                                                            |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Codex                                         | App-server `error` notification with `codexErrorInfo` `usageLimitExceeded` or `rateLimitExceeded` and `willRetry: false`; turn failures carrying the same codes                                | From the account rate-limit windows (`account/rateLimits/updated`); a turn refused before any snapshot arrives falls back to the "try again at …" time in Codex's message | `CodexAdapterV2.ts`, `provider/codexUsageLimits.ts`                               |
| Codex (usage)                                 | `account/rateLimits/updated`: used percent per window                                                                                                                                          | Window reset                                                                                                                                                              | Drives the usage-threshold offer                                                  |
| Claude Code                                   | SDK result with `terminal_reason: "blocking_limit"`, `api_error_status: 429`, an API retry message with status 429, or a limit message in the result; a gateway-wrapped 429 with "reset after" | Parsed from the gateway text when present                                                                                                                                 | `ClaudeAdapterV2.ts` (`providerFailureFromResult`, `providerFailureFromApiRetry`) |
| Grok                                          | ACP error code `-32003` (xAI rate limited)                                                                                                                                                     | Not reported                                                                                                                                                              | `provider-grok/src/server/adapter.ts`                                             |
| Mistral Vibe (ACP registry)                   | `_session/retrying` with category `rate_limited`, or its rate-limited request error                                                                                                            | Not reported                                                                                                                                                              | `provider-acp-registry/src/server/adapter.ts`                                     |
| Any ACP Registry agent (including Gemini CLI) | An ACP request error whose message reports an exhausted quota or rate limit: `RESOURCE_EXHAUSTED`, `429`, "quota exceeded", "usage limit", "rate limit", "too many requests"                   | Not reported                                                                                                                                                              | `messageReportsUsageLimit` in `provider-acp-registry/src/server/adapter.ts`       |
| Cursor                                        | None mapped; its limit errors arrive as `provider_error`                                                                                                                                       | —                                                                                                                                                                         | Manual handoff only                                                               |
| OpenCode                                      | Terminal HTTP 429; `provider.rate-limit`; `rate_limit_exceeded`, `FreeUsageLimitError`, quota/rate-limit text in the provider error or nested response body                                    | Not reliably reported                                                                                                                                                     | `provider-opencode/src/server/usageLimit.ts` (`openCodeFailureClass`)             |

## Adding a signal

Map the provider's terminal limit error to `makeProviderFailure({ class: "usage_limit", ... })`,
with `resetAt` when the provider names one. Keep transient, self-retried rate limits as retries.
Add a test that feeds the recorded error through the adapter and checks the class.
